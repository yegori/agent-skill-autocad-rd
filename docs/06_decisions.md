## Уточнение полномочий check-set (2026-10-30)

Проверка сохраняет исходную выдачу неизменной, но создаёт рабочие результаты в новой папке внутри `RDCI_WORK` / рабочей папки `W`.
Проверочные запуски AutoCAD, извлечение текстов и контрольная печать допустимы на копиях в рамках согласованного объёма; исправления — отдельная задача.
Размещение отчёта рядом с выдачей и обновление проектных записок требуют согласованного места записи; без него отчёт и проектная записка остаются в рабочей папке.
Запрос на проверку не разрешает менять пользовательские настройки печати: `check_papers` — без `-Add`, `plot_set` — с `-NoPaperCheck`.
Имена снимков DWG сохраняются из-за полей штампа; частный приём переименования изделий больше не является автоматическим шагом.

## Режимы check-set (2026-10-30)

Добавлены быстрая (состав/PDF без AutoCAD), целевая (конкретные вопросы/листы) и полная (все применимые этапы, включая DWG ↔ PDF) проверки.
Общий запрос без глубины требует выбора режима; тяжёлый конвейер не запускается автоматически. Однозначный запрос задаёт режим без повторного вопроса.
Копирование, обработка и отчёт ограничиваются выбранным объёмом. Быстрая/целевая проверка по умолчанию даёт краткий Markdown-отчёт, полная — Excel и проектную записку.
Отсутствие предыдущей выдачи не блокирует независимые проверки. Отсутствие DWG или инструментов фиксируется как ограничение, а не скрытое снижение глубины.

## Доказательность результатов check-set (2026-10-30)

Для каждого замечания обязательны место, наблюдаемые значения, основание и сохранённые доказательства; для сверки — оба источника.
Подтверждённость, серьёзность и статус исправления учитываются раздельно. Подтверждённое расхождение не определяет автоматически правильное инженерное значение.
Отчёт содержит состав и идентификацию снимка, матрицу фактически выполненных проверок и причины пропусков; нулевое число ошибок не подменяет охват.
Различия рендера, сообщения скриптов и отсутствие извлечённого текста требуют проверки контекста. Давность отсутствующей ссылки не делает её автоматически безвредной.
Вывод ограничивается охватом; окончательное решение о выпуске остаётся за ответственным инженером. Пример Excel — основа оформления, обязательные поля добавляются при подготовке отчёта.

## Загрузка .NET API СПДС (2026-11-04)

`TXTFIX` явно загружает `MapiBaseTypes`, затем `mapimgd` из установленного СПДС перед обработкой файлов.
Одного обработчика `AssemblyResolve` недостаточно на проверенном новом ПК. Загрузчик проверяет идентичность
сборок, не подменяет версии и ограничивает разрешение двумя именами; реальные DLL загружаются только внутри AutoCAD.
Сборка плагина включает `SpdsDependencies.cs`; изменение любого из двух исходников вызывает пересборку.
Добавлены 11 изолированных тестов с фиктивными DLL. Результат удалённого smoke-теста: 136 текстов,
`changed=0`, `mcs=0`, `ALLDONE`, исходный DWG не изменён. Проверка настоящих объектов СПДС остаётся отдельным этапом.

## Каталог проверок и граница MVP сервиса (2026-11-04)

Каталог группируется по S/F/P/C/V/R/Q без устаревшего общего деления «MVP/после MVP»:
этапы конкретного сервиса задаются его спецификацией. В rd-ci v0.3 сквозные сверки пилота и проверка штампов/xref
входят в MVP; выполнение исправлений остаётся следующим этапом. Добавлено требование F5 для xref штампа/общей цели
и согласованности общих реквизитов/оформления; готовность составного исполнителя пока частичная, не выполненная проверка.
Наличие в каталоге способа правки не даёт права применять её при проверке.

## Автономный вход/выход Pi (2026-11-04)

`docs/13_orchestrator.md` задаёт небольшой JSON-вход и manifest результата автономного задания:
`schema_version`, `job_id`, `status`, `summary`, `report_paths`, `artifact_paths`, `questions`.
Статус выполнения не подменяет оценку качества документации. Отчёты и артефакты — в новой явно заданной папке проекта;
сессия/журналы и промежуточные файлы — отдельно. При недостающем контексте — `needs_input`, а не ожидание диалога.
Методы и содержание отчёта остаются здесь; запуск процесса и техническая валидация файлов — в rd-ci.
Быстрая проверка не даёт разрешения запускать CAD; протокол не разрешает правки, установку/настройку ПО или отправку сообщений.

## PMP и ограниченный автономный PDF (2026-11-05)

Отсутствие PMP не является блокировкой стандартного ISO/ANSI. `check_env.ps1` отделяет необязательное
предупреждение от отсутствующей обязательной зависимости; добавлены 6 изолированных проверок диагностики без CAD.
Формат макета проверяется отдельно `check_papers.ps1` без `-Add`; недоступный нестандартный формат не добавляется автоматически.
Для автономной печати/сшивки manifest должен перечислять листовые и сводный PDF, отчёт — проверку их страниц/размеров.
Внутреннее сокращённое имя копии toolkit и сохранение полного имени по заданию требуют явной совместимости;
исходники не переименовываются. Первое задание безопасно вернуло `needs_input` до CAD; повторный тест — отдельно.

## Ограниченный профиль очереди (2026-11-05)

В протокол добавлен `execution_profile: files_only`: только чтение/поиск файлов и запись отчёта, без shell/CAD/PDF-рендера.
Это не упрощённая полная проверка: вне доступного объёма — `needs_input`, без выдуманных снимков/хешей.
Явно запрошенный осмотр одного текстового файла может завершиться отчётом по его содержимому с указанными ограничениями.
Методы и результат по-прежнему определяет пакет; блокировка процесса/очередь и ID запуска — ответственность rd-ci.

Ранее общий журнал сервиса сохранён в истории Git и в [rd-ci/docs/06_decisions.md](https://github.com/yegori/rd-ci/blob/master/docs/06_decisions.md).
Новые сервисные решения вносить туда, проектные записки — в `_claude` рядом с чертежами.
